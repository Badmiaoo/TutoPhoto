# Dépôt public : ce qui ne doit jamais y entrer

Décidé par Julien le 7 novembre 2026 : le dépôt devient public, condition pour publier le site gratuitement sur GitHub Pages. Sur GitHub.com, GitHub Pages est disponible pour les dépôts publics avec l'offre gratuite, et pour les dépôts privés seulement avec une offre payante ([« GitHub Pages limits »](https://docs.github.com/en/pages/getting-started-with-github-pages/github-pages-limits), en tête de la page) ; même alors, hors GitHub Enterprise Cloud, le site publié reste public ([« Creating a GitHub Pages site »](https://docs.github.com/en/pages/getting-started-with-github-pages/creating-a-github-pages-site), avertissement de la section « Creating your site »). Sources lues dans le dépôt `github/docs`, commit `8cd1075` du 6 novembre 2026 (sources `github-pages-limits` et `github-pages-creating-site`) ; l'adresse du second lien est déduite du chemin de son fichier dans ce dépôt, la page n'ayant pas pu être ouverte (`docs.github.com` ne se joint pas d'ici). Écrit ainsi dans la version 0.4.14 (constat LIC-10 de l'audit, `docs/audit/licences-scripts-ci.md`) : la page des limites ne dit pas que le site reste public, et une organisation sous GitHub Enterprise Cloud peut publier un site en privé.

## Ce qui ne doit jamais être publié

- Secrets : jetons d'API, clés, mots de passe, clés privées. Un secret dont un workflow a besoin va dans les secrets GitHub du dépôt, jamais dans un fichier.
- Données personnelles : adresses électroniques (seules les adresses « noreply » sont admises), numéros de téléphone, adresses postales.
- Liens vers des ressources privées : documents Claude, Google Docs ou Drive, Dropbox, Notion.
- Chemins locaux qui révèlent un nom d'utilisateur (`/Users/…`, `/home/…`, `C:\Users\…`).

Exceptions acceptées par Julien : son nom, comme auteur des commits, avec son adresse « noreply » de GitHub, et comme titulaire du copyright dans `LICENSE` (7 novembre 2026, `docs/historique.md`). Cette page disait « auteur des commits de fusion » jusqu'à la version 0.4.13, alors que la décision porte sur les commits, dont Julien est l'auteur, fusions ou non (constat LIC-08 de l'audit).

## Contrôles

- `scripts/check_public.py` cherche ces informations dans tous les fichiers suivis par git (le chemin de chacun, et le contenu des fichiers de texte) et, avec `--commits`, dans les commits : noms des auteurs et des committers, messages, lignes ajoutées par chaque commit et chemins des fichiers qu'il introduit. Les adresses des auteurs et des committers doivent être des adresses « noreply » ou d'un domaine d'exemple (`example.com`, `.test`…) ; celle de GitHub est admise avec ou sans numéro devant le pseudo, la forme sans numéro étant celle d'un compte qui l'a choisie avant le 18 juillet 2017 ([documentation GitHub](https://raw.githubusercontent.com/github/docs/d7487f5debb5a5a2a6e65e6f9fa539266f5f8db6/content/account-and-profile/reference/email-addresses-reference.md), source `github-noreply-email`). Il tourne dans la CI de chaque pull request et de `main`, sur tout l'historique des branches et des étiquettes (`--commits all`). Les messages de commit ne sont contrôlés que depuis le 8 novembre 2026 (voir ci-dessous) ; les noms, les chemins et les lignes ajoutées, depuis la version 0.3.84 (constats LIC-01 et LIC-03 de l'audit, `docs/audit/licences-scripts-ci.md`).
- Pourquoi les lignes ajoutées : les pull requests sont fusionnées par un commit de fusion, sans squash, donc chaque commit intermédiaire est publié sur `main`. Ce qu'un commit ajoute et qu'un commit suivant retire reste dans l'historique publié, que l'état final des fichiers ne montre plus. Chaque ligne est lue dans le commit qui l'apporte : pour un commit ordinaire, les lignes ajoutées de son diff ; pour un commit de fusion, celles qu'aucun de ses parents n'a, que le diff combiné de git marque « + » pour chaque parent ([format du diff combiné](https://raw.githubusercontent.com/git/git/03b41523c576f26ad34085378717a0c1b287470f/Documentation/diff-generate-patch.adoc) et [option `--diff-merges`](https://raw.githubusercontent.com/git/git/03b41523c576f26ad34085378717a0c1b287470f/Documentation/diff-options.adoc) de git 2.56.1, sources `git-2-56-1-diff-combine` et `git-2-56-1-diff-merges`) ; le premier commit, comparé à un arbre vide. Un fichier que git montre comme binaire (« Binary files … differ ») est relu en entier dans sa nouvelle version s'il n'a pas d'octet nul dans ses 8 000 premiers octets : un fichier de texte dont la version d'avant était binaire, ou qu'un attribut de git déclare binaire. Un chemin est lu dans le commit qui l'introduit (fichier ajouté, ou renommé sous ce chemin), écrit tel quel, sans l'échappement de git. Sur tout l'historique au commit 8f63c7c (branches et étiquettes) : 566 commits, 72 839 lignes ajoutées et 239 chemins introduits, lus en 4 à 6 secondes selon la machine.
- Tolérances : `scripts/check_public_historique.txt` liste les problèmes déjà publiés, que l'historique non réécrit garde et qui arrêteraient sinon la CI de toutes les pull requests suivantes. Chaque tolérance vaut pour un commit, un endroit (son message ; ses lignes ajoutées et les chemins qu'il introduit ; ou l'identité de son auteur et de son committer, noms et adresses) et un type de problème, et pour rien d'autre. Une tolérance ne s'y inscrit qu'après le signalement de la fuite à Julien, avec la date du signalement, par une pull request où elle se relit (retouche gardée du constat réfuté LIC-06). Il y en a deux sortes : les messages des 28 commits de la fuite du 8 novembre 2026 (plus bas), et le lien du Claude Doc d'origine que le commit `e89680d` a ajouté à `REPRISE.md` (« Avant le passage en public »), seul cas que la lecture des lignes ajoutées trouve dans tout l'historique.
- Le titre et la description de chaque pull request, qui ne sont pas dans git, passent par le même script (`--pull-request`, qui lit le fichier de l'événement GitHub), dans le workflow `.github/workflows/description.yml`, à chaque création ou modification. Ajouté le 11 novembre 2026 (voir ci-dessous).
- [gitleaks](https://github.com/gitleaks/gitleaks/tree/v8.30.1) 8.30.1 (licence MIT) cherche les secrets dans tout l'historique git, dans la même CI. Le binaire est téléchargé depuis la release officielle et vérifié par son empreinte SHA-256 avant d'être lancé.
- Côté GitHub, pour un dépôt public : la recherche de secrets (secret scanning) tourne automatiquement et gratuitement ([documentation](https://docs.github.com/en/code-security/concepts/secret-security/secret-scanning)), et la protection des pushes pour les utilisateurs est active par défaut ([documentation](https://docs.github.com/en/code-security/how-tos/secure-your-secrets/prevent-future-leaks/manage-user-push-protection)). Sources lues dans le dépôt `github/docs`, commit `8cd1075` du 6 novembre 2026.

## Ce que les contrôles ne lisent pas

Écrit dans la version 0.3.84 (constats LIC-02 et LIC-03 de l'audit) : ce qui suit échappe à `scripts/check_public.py` ; gitleaks en arrête une partie (dernier point), le reste n'est vu qu'à la relecture.

- Le contenu d'un fichier, ou d'une version d'un fichier, qui a un octet nul dans ses 8 000 premiers octets : un fichier binaire, ou un fichier de texte enregistré en UTF-16, où chaque caractère ASCII occupe deux octets dont un nul (essai du 21 novembre 2026 : une adresse électronique dans un tel fichier n'est pas signalée). Son chemin, lui, est lu. Le 21 novembre 2026, les 24 fichiers binaires suivis sont ceux de la scène de parc, sous `app/public/scenes/`.
- Les étiquettes (tags) : ni leur message, ni le nom et l'adresse de qui les pose. Le 21 novembre 2026, les 86 étiquettes sont posées par le compte du workflow `tag.yml`, avec son adresse « noreply », et leur message est la section du changelog, contrôlée comme fichier.
- Les adresses postales : aucun motif ne les reconnaît sans refuser du texte ordinaire. Ce point de la règle n'est contrôlé par aucun script.
- Les commits qu'aucune branche ni étiquette ne contient plus, mais que GitHub garde sous `refs/pull/<n>/head` (pull request fermée sans fusion, branche supprimée) : la CI ne récupère que les branches, les étiquettes et la pull request en cours. Le 21 novembre 2026, un seul commit est dans ce cas, celui de la pull request 69 ; le script, lancé sur une copie qui récupère aussi ces références, n'y trouve rien (contrôle final de la version 0.3.84).
- Les secrets d'une forme que le script ne connaît pas. Il reconnaît des formats de jetons et de clés connus, et un secret écrit entre guillemets après un nom comme `password`, `secret` ou `api_key` ; gitleaks complète dans la CI. Essai du 21 novembre 2026, gitleaks 8.30.1 lancé comme dans la CI, sur des valeurs fabriquées dans un dépôt d'essai, un cas par fichier : gitleaks arrête un mot de passe ou une clé écrits sans guillemets après un nom comme `password`, `secret`, `key` ou `token` quand la valeur a de 10 à 150 caractères pris parmi les lettres, les chiffres, « _ », « . », « = » et « - », ou au moins 12 pris parmi les lettres, les chiffres, « + » et « / », une entropie d'au moins 3,5, et qu'elle ne contient aucun des 1 446 mots de sa liste d'exclusion (« admin », « account »…) (règle `generic-api-key` de sa [configuration par défaut](https://raw.githubusercontent.com/gitleaks/gitleaks/83d9cd684c87d95d656c1458ef04895a7f1cbd8e/config/gitleaks.toml), l. 637-2128 : valeur l. 640, seuil l. 641, liste l. 664-2111 ; source `gitleaks-8-30-1-config`) : `password:` dans un fichier YAML, `API_KEY=` dans un fichier d'environnement, un jeton de 32 chiffres hexadécimaux affecté à un nom en `_API_TOKEN`, que le script laisse passer. Les deux arrêtent une clé privée PGP. Échappent aux deux, écrits sans guillemets : un mot de passe de moins de dix caractères, une phrase de passe faite de mots séparés d'espaces, une valeur qui contient un autre signe (« # », « ! », « @ »…) ou un mot de la liste d'exclusion ; et un en-tête « Authorization: Token … » ou « Authorization: Bearer … » hors d'une commande `curl` (la règle `curl-auth-header`, l. 359-362, demande `curl` et `-H`). Entre guillemets, une valeur d'au moins huit caractères, sans espace ni guillemet, écrite après `password`, `passwd`, `pwd`, `secret`, `api_key`, `access_token`, `auth_token` ou « mot de passe », est arrêtée par le script (« secret écrit en clair »). gitleaks ne lit pas non plus ce qu'un commit de fusion ajoute lui-même : dans le même essai, une valeur qu'il arrête dans un commit ordinaire passe quand une fusion l'ajoute ; dans la CI du commit f0b7545, il dit avoir lu 478 commits, quand `scripts/check_public.py` en lit 569, dont 90 commits de fusion. `scripts/check_public.py`, lui, lit ces lignes, pour ses propres motifs. gitleaks ne tourne que dans la CI, donc après l'envoi du commit : ce qu'il trouve est déjà publié (« Si quelque chose a fuité »).

Refus et passages à tort connus du script, aucun dans le dépôt le 21 novembre 2026 (relecture de la version 0.3.84) : un nom de code fait de « session_ » suivi d'un mot d'au moins dix lettres, sans espace (« session_ » puis « parameters »), est pris pour un identifiant de session Claude, et un nom d'image pour écran dense, fait d'un nom, d'une arobase, de « 2x » et de l'extension, pour une adresse électronique ; un identifiant de session collé après « _ » passe. Écrits en clair, ces exemples seraient refusés par le script.

## Pull request d'un tiers

Écrit dans la version 0.4.14, d'après la section du rapport des licences sur ce qu'un contributeur extérieur peut obtenir par une pull request (`docs/audit/licences-scripts-ci.md`), que son contre-avis ne conteste pas. La CI d'une pull request fait tourner les fichiers de cette pull request : ses workflows, ses scripts, ses dépendances, et les contrôles tels qu'elle les a écrits. Pour la pull request d'un tiers, une CI verte ne prouve donc rien sur les fichiers qui font les contrôles ou que la CI exécute : `.github/`, `scripts/` (dont `scripts/check_public_historique.txt`, la liste des tolérances), `schemas/`, `requirements.txt` et, dans `app/`, `package.json`, `package-lock.json`, `scripts/`, `tests/`, `vite.config.ts`, `vite.activites.config.ts`, `tsconfig.json` et `tsconfig.node.json`. Ces fichiers se relisent avant d'approuver l'exécution des workflows, et avant de fusionner. Le dépôt demande cette approbation pour tout contributeur extérieur (« Require approval for all external contributors », réglage fait par Julien le 15 novembre 2026, `docs/historique.md` ; non relu par Claude). Après la fusion, le code est publié sur le site (`pages.yml`), et `scripts/changelog.py` tourne avec le droit d'écrire dans le dépôt (`tag.yml`) : la relecture avant la fusion est la seule barrière.

## Images

Une image faite par le projet (capture d'écran, photo de Julien) est vidée de ses métadonnées avant d'entrer dans le dépôt : le contrôle ne lit pas le contenu d'un fichier binaire. Les fichiers de tiers des scènes, eux, ne sont pas retouchés pour en retirer les métadonnées : chacun est tel que son origine le fournit, ou modifié et déclaré comme tel dans le champ `changes` de son modèle, que demande la licence CC BY (`docs/licences.md`). Le 21 novembre 2026, seules les quatre textures de couleur des personnages sont modifiées, réduites de 8192 à 2048 px de côté, sans autre métadonnée qu'un en-tête JFIF. Le manifeste de la scène garde l'adresse d'origine de chaque fichier et l'empreinte du fichier tel qu'il est dans le dépôt. Règle écrite dans la version 0.3.84, d'après la contre-vérification du constat LIC-03, précisée par la relecture de cette version (les quatre textures réduites).

## Si quelque chose a fuité

Un dépôt public peut être copié dès qu'un commit est poussé : effacer le fichier ne suffit pas. Un secret qui a fuité doit être révoqué et remplacé tout de suite chez le service qui l'a émis. L'historique publié n'est pas réécrit (règle du dépôt) ; on le signale à Julien. Une fois la fuite signalée, et seulement alors, la tolérance qui laisse passer la CI s'inscrit dans `scripts/check_public_historique.txt` (empreinte complète du commit, endroit, type de problème), avec la date du signalement, par une pull request ; un nom ou une adresse d'auteur ou de committer se tolèrent aussi (endroit « identité »).

Les commits concernés sont listés dans `scripts/check_public_historique.txt` : l'historique publié n'est pas réécrit, et le contrôle tolère ce seul problème, dans le message de ces seuls commits.

Les modifier n'aurait de toute façon pas effacé l'ancienne version : « Anyone with read access to a repository can view a comment's edit history » ([documentation GitHub](https://docs.github.com/en/communities/moderating-comments-and-conversations/tracking-changes-in-a-comment), source lue dans le dépôt `github/docs`, branche `main`, le 8 novembre 2026).

## Constat du 11 novembre 2026 : liens de session Claude dans les descriptions des pull requests

- Les descriptions de 21 pull requests, toutes de la même session de travail que la fuite du 8 novembre, finissaient par un pied « Generated by Claude Code » dont le lien mène à la session (claude.ai/code/session_…) : #15 à #27, #30, #34, #36, #41, #45, #46, #47 et #49.
- Cause : à la création d'une pull request, l'outil GitHub de Claude remplace le pied de la description par ce pied, qui contient le lien de la session. Pour la #49, la description envoyée finissait par « 🤖 Generated with [Claude Code](https://claude.com/claude-code) » ; GitHub a enregistré l'autre pied. Une modification de la description, elle, garde le texte envoyé tel quel. Les autres pull requests depuis la #15 n'ont pas ce pied : leur description a vraisemblablement été réécrite après la création, et leur historique d'édition contient alors le lien. Ce n'est pas vérifié, car les outils de Claude ne lisent pas cet historique.
- `scripts/check_public.py` ne voyait rien : il contrôle les fichiers et les commits, pas les descriptions, qui ne sont pas dans git.
- Nature : la même que le 8 novembre. C'est un lien vers une ressource privée, que seul le propriétaire de la session peut ouvrir ; il ne contient aucun secret ni donnée personnelle.
- Signalé à Julien le 11 novembre 2026. Ses décisions, le même jour :
  - retirer le lien des 21 descriptions. C'est fait le jour même : seul le pied a changé, et une relecture confirme que chaque description enregistrée est identique au texte voulu. Le lien reste dans l'historique d'édition (voir la documentation GitHub citée plus haut). Les #1 à #14 restent en l'état, selon la décision du 8 novembre ;
  - pour les pull requests suivantes : Claude les crée, puis réécrit aussitôt la description sans le lien. Le workflow `description.yml` échoue tant que le lien y est. Une pull request n'est donc jamais fusionnée avec ce lien, mais il reste dans l'historique d'édition de chacune.
- Premier essai du contrôle, sur la #50 : il a échoué sur la description créée, puis réussi sur la description réécrite. Mais sa première version passait le titre et la description à l'étape par « env: », et Actions écrit ces variables en clair au début du journal de l'étape. Le journal de ce premier passage, public pour ce dépôt, contenait donc le lien. Claude a supprimé ce journal le jour même, comme le prévoit la décision de retirer le lien, et a vérifié qu'il n'est plus lisible. Le script lit désormais le fichier de l'événement (`$GITHUB_EVENT_PATH`), qu'Actions n'affiche pas.
