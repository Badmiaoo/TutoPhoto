# Dépôt public : ce qui ne doit jamais y entrer

Décidé par Julien le 7 novembre 2026 : le dépôt devient public, condition pour publier le site gratuitement sur GitHub Pages. GitHub Pages est disponible pour les dépôts publics avec l'offre gratuite, et pour les dépôts privés seulement avec une offre payante ; même alors, le site publié reste public ([documentation GitHub Pages](https://docs.github.com/en/pages/getting-started-with-github-pages/github-pages-limits), source lue dans le dépôt `github/docs`, commit `8cd1075` du 6 novembre 2026).

## Ce qui ne doit jamais être publié

- Secrets : jetons d'API, clés, mots de passe, clés privées. Un secret dont un workflow a besoin va dans les secrets GitHub du dépôt, jamais dans un fichier.
- Données personnelles : adresses électroniques (seules les adresses « noreply » sont admises), numéros de téléphone, adresses postales.
- Liens vers des ressources privées : documents Claude, Google Docs ou Drive, Dropbox, Notion.
- Chemins locaux qui révèlent un nom d'utilisateur (`/Users/…`, `/home/…`, `C:\Users\…`).

Exceptions acceptées par Julien : son nom, comme auteur des commits de fusion avec son adresse « noreply » de GitHub, et comme titulaire du copyright dans `LICENSE`.

## Contrôles

- `scripts/check_public.py` cherche ces informations dans tous les fichiers suivis par git (le chemin de chacun, et le contenu des fichiers de texte) et, avec `--commits`, dans les commits : noms et adresses des auteurs et des committers (seules les adresses « noreply » sont admises ; celle de GitHub, avec ou sans numéro devant le pseudo, la forme sans numéro étant celle d'un compte qui l'a choisie avant le 18 juillet 2017 : [documentation GitHub](https://raw.githubusercontent.com/github/docs/d7487f5debb5a5a2a6e65e6f9fa539266f5f8db6/content/account-and-profile/reference/email-addresses-reference.md), source `github-noreply-email`), messages, lignes ajoutées par chaque commit et chemins de leurs fichiers. Il tourne dans la CI de chaque pull request et de `main`, sur tout l'historique des branches et des étiquettes (`--commits all`). Les messages de commit ne sont contrôlés que depuis le 8 novembre 2026 (voir ci-dessous) ; les noms, les chemins et les lignes ajoutées, depuis la version 0.3.84 (constats LIC-01 et LIC-03 de l'audit, `docs/audit/licences-scripts-ci.md`).
- Pourquoi les lignes ajoutées : les pull requests sont fusionnées par un commit de fusion, sans squash, donc chaque commit intermédiaire est publié sur `main`. Ce qu'un commit ajoute et qu'un commit suivant retire reste dans l'historique publié, que l'état final des fichiers ne montre plus. Chaque ligne est lue dans le commit qui l'apporte : pour un commit ordinaire, les lignes ajoutées de son diff ; pour un commit de fusion, celles qu'aucun de ses parents n'a, que le diff combiné de git marque « + » pour chaque parent ([format du diff combiné](https://raw.githubusercontent.com/git/git/03b41523c576f26ad34085378717a0c1b287470f/Documentation/diff-generate-patch.adoc) et [option `--diff-merges`](https://raw.githubusercontent.com/git/git/03b41523c576f26ad34085378717a0c1b287470f/Documentation/diff-options.adoc) de git 2.56.1, sources `git-2-56-1-diff-combine` et `git-2-56-1-diff-merges`) ; le premier commit, comparé à un arbre vide. Sur tout l'historique, le 21 novembre 2026 : 566 commits et 72 839 lignes ajoutées, lus en 4 secondes.
- Tolérances : `scripts/check_public_historique.txt` liste les problèmes déjà publiés, que l'historique non réécrit garde et qui arrêteraient sinon la CI de toutes les pull requests suivantes. Chaque tolérance vaut pour un commit, un endroit (son message, ou ses lignes ajoutées et leurs chemins) et un type de problème, et pour rien d'autre. Une tolérance ne s'y inscrit qu'après le signalement de la fuite à Julien, avec la date du signalement, par une pull request où elle se relit (retouche gardée du constat réfuté LIC-06). Il y en a deux sortes : les messages des 28 commits de la fuite du 8 novembre 2026 (plus bas), et le lien du Claude Doc d'origine que le commit `e89680d` a ajouté à `REPRISE.md` (« Avant le passage en public »), seul cas que la lecture des lignes ajoutées trouve dans tout l'historique.
- Le titre et la description de chaque pull request, qui ne sont pas dans git, passent par le même script (`--pull-request`, qui lit le fichier de l'événement GitHub), dans le workflow `.github/workflows/description.yml`, à chaque création ou modification. Ajouté le 11 novembre 2026 (voir ci-dessous).
- [gitleaks](https://github.com/gitleaks/gitleaks/tree/v8.30.1) 8.30.1 (licence MIT) cherche les secrets dans tout l'historique git, dans la même CI. Le binaire est téléchargé depuis la release officielle et vérifié par son empreinte SHA-256 avant d'être lancé.
- Côté GitHub, pour un dépôt public : la recherche de secrets (secret scanning) tourne automatiquement et gratuitement ([documentation](https://docs.github.com/en/code-security/concepts/secret-security/secret-scanning)), et la protection des pushes pour les utilisateurs est active par défaut ([documentation](https://docs.github.com/en/code-security/how-tos/secure-your-secrets/prevent-future-leaks/manage-user-push-protection)). Sources lues dans le dépôt `github/docs`, commit `8cd1075` du 6 novembre 2026.

## Ce que les contrôles ne lisent pas

Écrit dans la version 0.3.84 (constats LIC-02 et LIC-03 de l'audit) : ce qui suit n'est vu qu'à la relecture.

- Le contenu des fichiers binaires : pour `scripts/check_public.py`, un fichier qui a un octet nul dans ses 8 000 premiers octets ; dans un commit, un fichier que git montre comme binaire (« Binary files … differ »). Un fichier de texte enregistré en UTF-16 en fait partie, chaque lettre latine y occupant deux octets dont un nul (essai du 21 novembre 2026 : une adresse électronique dans un tel fichier n'est pas signalée). Leur chemin, lui, est lu. Le 21 novembre 2026, les 24 fichiers binaires suivis sont ceux de la scène de parc, sous `app/public/scenes/`.
- Les étiquettes (tags) : ni leur message, ni le nom et l'adresse de qui les pose. Le 21 novembre 2026, les 86 étiquettes sont posées par le compte du workflow `tag.yml`, avec son adresse « noreply », et leur message est la section du changelog, contrôlée comme fichier.
- Les adresses postales : aucun motif ne les reconnaît sans refuser du texte ordinaire. Ce point de la règle n'est contrôlé par aucun script.
- Les secrets d'une forme que le script ne connaît pas. Il reconnaît des formats de jetons et de clés connus, et un secret écrit entre guillemets après un nom comme `password`, `secret` ou `api_key` ; gitleaks complète dans la CI. Essai du 21 novembre 2026, gitleaks 8.30.1 lancé comme dans la CI, sur des valeurs fabriquées dans un dépôt d'essai : gitleaks arrête un mot de passe ou une clé écrits sans guillemets (`password:` dans un fichier YAML, `API_KEY=` dans un fichier d'environnement, un jeton de 32 chiffres hexadécimaux affecté à un nom en `_API_TOKEN`), que le script laisse passer, et une clé privée PGP, que le script arrête aussi ; un en-tête « Authorization: Token … » ou « Authorization: Bearer … » hors d'une commande `curl` échappe aux deux. gitleaks ne tourne que dans la CI, donc après l'envoi du commit : ce qu'il trouve est déjà publié (« Si quelque chose a fuité »).

## Images

Une image faite par le projet (capture d'écran, photo de Julien) est vidée de ses métadonnées avant d'entrer dans le dépôt : le contrôle ne lit pas le contenu d'un fichier binaire. Les fichiers de tiers des scènes, eux, restent identiques à leur origine : le manifeste de la scène garde l'empreinte et l'adresse d'origine de chacun, pour qu'on puisse les comparer à l'original, et une modification d'un fichier sous CC BY se déclare dans son champ `changes` (`docs/licences.md`). Règle écrite dans la version 0.3.84, telle que la contre-vérification du constat LIC-03 la borne.

## Si quelque chose a fuité

Un dépôt public peut être copié dès qu'un commit est poussé : effacer le fichier ne suffit pas. Un secret qui a fuité doit être révoqué et remplacé tout de suite chez le service qui l'a émis. L'historique publié n'est pas réécrit (règle du dépôt) ; on le signale à Julien. Une fois la fuite signalée, et seulement alors, la tolérance qui laisse passer la CI s'inscrit dans `scripts/check_public_historique.txt` (empreinte complète du commit, endroit, type de problème), avec la date du signalement, par une pull request.

## Fuite du 8 novembre 2026 : liens de session Claude dans les messages de commit

- Les 28 commits faits par Claude du 7 au 8 novembre 2026, avant la version 0.3.9, finissent par une ligne « Claude-Session » qui donne l'adresse de la session de travail de Claude (claude.ai/code/session_…). Les descriptions des pull requests #1 à #14 contiennent la même adresse.
- C'est un lien vers une ressource privée : seul le propriétaire de la session peut l'ouvrir. Aucun secret ni donnée personnelle n'y figure.
- Cause : `scripts/check_public.py` ne lisait pas les messages de commit, et son motif ne couvrait pas ces adresses. Les deux sont corrigés dans la version 0.3.9. Les commits concernés sont listés dans `scripts/check_public_historique.txt` : l'historique publié n'est pas réécrit, et le contrôle tolère ce seul problème, dans le message de ces seuls commits.
- Signalé à Julien le 8 novembre 2026. Décision de Julien, le même jour : les descriptions des pull requests #1 à #14 restent en l'état, le lien ne s'ouvrant pas pour les autres. Les modifier n'aurait de toute façon pas effacé l'ancienne version : « Anyone with read access to a repository can view a comment's edit history » ([documentation GitHub](https://docs.github.com/en/communities/moderating-comments-and-conversations/tracking-changes-in-a-comment), source lue dans le dépôt `github/docs`, branche `main`, le 8 novembre 2026).

## Constat du 11 novembre 2026 : liens de session Claude dans les descriptions des pull requests

- Les descriptions de 21 pull requests, toutes de la même session de travail que la fuite du 8 novembre, finissaient par un pied « Generated by Claude Code » dont le lien mène à la session (claude.ai/code/session_…) : #15 à #27, #30, #34, #36, #41, #45, #46, #47 et #49.
- Cause : à la création d'une pull request, l'outil GitHub de Claude remplace le pied de la description par ce pied, qui contient le lien de la session. Pour la #49, la description envoyée finissait par « 🤖 Generated with [Claude Code](https://claude.com/claude-code) » ; GitHub a enregistré l'autre pied. Une modification de la description, elle, garde le texte envoyé tel quel. Les autres pull requests depuis la #15 n'ont pas ce pied : leur description a vraisemblablement été réécrite après la création, et leur historique d'édition contient alors le lien. Ce n'est pas vérifié, car les outils de Claude ne lisent pas cet historique.
- `scripts/check_public.py` ne voyait rien : il contrôle les fichiers et les commits, pas les descriptions, qui ne sont pas dans git.
- Nature : la même que le 8 novembre. C'est un lien vers une ressource privée, que seul le propriétaire de la session peut ouvrir ; il ne contient aucun secret ni donnée personnelle.
- Signalé à Julien le 11 novembre 2026. Ses décisions, le même jour :
  - retirer le lien des 21 descriptions. C'est fait le jour même : seul le pied a changé, et une relecture confirme que chaque description enregistrée est identique au texte voulu. Le lien reste dans l'historique d'édition (voir la documentation GitHub citée plus haut). Les #1 à #14 restent en l'état, selon la décision du 8 novembre ;
  - pour les pull requests suivantes : Claude les crée, puis réécrit aussitôt la description sans le lien. Le workflow `description.yml` échoue tant que le lien y est. Une pull request n'est donc jamais fusionnée avec ce lien, mais il reste dans l'historique d'édition de chacune.
- Premier essai du contrôle, sur la #50 : il a échoué sur la description créée, puis réussi sur la description réécrite. Mais sa première version passait le titre et la description à l'étape par « env: », et Actions écrit ces variables en clair au début du journal de l'étape. Le journal de ce premier passage, public pour ce dépôt, contenait donc le lien. Claude a supprimé ce journal le jour même, comme le prévoit la décision de retirer le lien, et a vérifié qu'il n'est plus lisible. Le script lit désormais le fichier de l'événement (`$GITHUB_EVENT_PATH`), qu'Actions n'affiche pas.

## Avant le passage en public

Audit du 7 novembre 2026 : aucun secret, aucune adresse électronique hors « noreply ». Le seul lien vers une ressource privée, celui du Claude Doc d'origine dans `REPRISE.md`, a été retiré de la version courante. Il reste dans l'historique, mais le document qu'il désigne est privé et inaccessible aux autres. Depuis la version 0.3.84, qui lit les lignes ajoutées par chaque commit, il est toléré dans les ajouts du commit `e89680d`, qui l'a apporté (`scripts/check_public_historique.txt`).
